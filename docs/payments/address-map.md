# Postal address map: outbound payments

Rule: `docs/scheme-bulletins/2026-11-structured-postal-address.md` (November 2026). Issue #2.

## Where an address enters

| Point | Code | Notes |
|---|---|---|
| `POST /api/v1/outbound-payments/payloads` | `PaymentController.payloads` | Renders the three payloads, returns them, publishes nothing. |
| `POST /api/v1/outbound-payments` | `PaymentController.create` | Renders, publishes the event, returns the payloads. |
| Request model | `PaymentInstruction.Party.addressLines` (debtor and creditor) | 1-3 free-text lines, 35 chars, SWIFT X character set. Unchanged by this work. |

## Where it is stored

| Store | Code | Notes |
|---|---|---|
| No database table | — | No entity, repository or table in any package holds a payment address. |
| Kafka topic `outbound-payments` | `PaymentPublisher.publish` | The event is the only durable copy the service writes. Key = `endToEndId`. |
| Recorded corpus | `payloads/recorded/PAY*/{input.json,mt103.txt,pacs008.xml,event.json}` | Pre-rule baseline, generated by `PaymentCorpus`. Left untouched; it is what the replay compares against. |

## Where it is written out

| Format | Before | After | Code |
|---|---|---|---|
| MT103 ordering customer | `:50K:/IBAN`, name, raw lines | `:50F:/IBAN`, `1/name`, `2/` address details, `3/CC/Town` | `PaymentRenderer.partyText` |
| MT103 beneficiary | `:59:/IBAN`, name, raw lines | `:59F:/IBAN`, same layout | `PaymentRenderer.partyText` |
| pacs.008 `Dbtr`/`Cdtr` | `<PstlAdr>` with `AdrLine` only | `StrtNm, BldgNb, BldgNm, PstBx, PstCd, TwnNm, Ctry` (schema order); up to 2 `AdrLine` only when a line cannot be classified (hybrid) | `PaymentRenderer.xmlParty` |
| Kafka event `payment.debtor/creditor` | `addressLines` | `postalAddress` in the same position: `streetName, buildingNumber, buildingName, postBox, postCode, townName, country[, addressLines]` | `PaymentRenderer.withPostalAddress` |
| REST response | same three payloads | same three payloads | `PaymentController` |

All three formats are built from one `PostalAddress` produced by `PostalAddressStructurer`, so they cannot disagree.

## How the structure is found (no guessing)

`PostalAddressStructurer` uses fixed layout patterns only. Every value is copied verbatim from the input lines; there is no town list.

- Country: a two-letter ISO 3166 code ending a line. If none is stated, the IBAN country is used only when the BIC country agrees; otherwise the payment is held.
- Post box: `P.O. Box N`. Post code: 4-5 digits or a UK two-part code.
- Street: building number + words ending in a street designator (`Lane`, `Street`, `Road`, ...).
- Town: only in an unambiguous position: after a comma following the street, next to a post code on the same line, or between the street and a post code on one line.
- A words-only line directly before the street line is the building name. Anything else becomes an `AdrLine` (max 2).
- No town, more than 2 unclassified lines, or an MT103 block over 4 lines of 35 characters: `AddressIncompleteException`. The API returns HTTP 422 and nothing is published. These payments are listed in `operations-missing-town.md`.

## Proof

`PaymentReplayTest` replays every recorded payment, masks only the address regions, requires everything else to be byte for byte identical, checks each new address against the rule, and checks that every word of the original address survives. It regenerates `parity-report.md` and `operations-missing-town.md` and fails if the committed copies differ.
